## Types of Estimations

Load estimation (QPS) - Predict the expected number of requests per second, data volume, or user traffic (DAU) for the system.
Storage estimation: Estimate the amount of storage required to handle the data generated by the system.
Bandwidth estimation: Determine the network bandwidth needed to support the expected traffic and data transfer.
Latency estimation: Predict the response time and latency of the system based on its architecture and components.
Resource estimation: Estimate the number of servers, CPUs, or memory required to handle the load and maintain desired performance levels.

## Key Characteristics of Distributed Systems

Scalability - Increase #users/data/work w/o any impact to perf. Horizontal, Vertical (MySQL)
Reliability - continue working correctly in case of errors
Fault Tolerance - gracefully handle failures and continue operating, may be at reduced level
Availability - system should be up
Efficiency - do more with less resources
Serviceability or Manageability
Throughput (or bandwidth) - number of items delivered in a given time unit

## Load Balancing

We can add LBs at three places:
- Between the user and the web server
- Between web servers and an internal platform layer, like application servers or cache servers
- Between internal platform layer and database.

Redundant Load Balancers - Active, passive. Each LB monitors the health of the other and, since both of them are equally capable of serving traffic and failure detection, in the event the main load balancer fails, the second load balancer takes over.

Load Balancing Algorithms (trick to memorize?)
1. Round Robin
2. Least Connections
3. Weighted Round Robin
4. Weighted Least Connections
5. IP Hash
6. Least Response Time
7. Random
8. Least Bandwidth
9. Custom Load

## Proxies

Intermediate server between client & server that intercepts requests, caches, filters, or routes them.

🔄 FORWARD PROXY (Hides Client Identity):
Why Hide: Prevent server from seeing client IP (privacy), block targeted attacks on client, enforce access control policies, comply with data residency laws.
Benefits: Protects client privacy, caches responses, filters malicious requests, deduplicates.
Business: Corporate networks (employee privacy), ISPs, VPN services, geo-blocking bypass.

WHY HIDE CLIENT IDENTITY (Forward Proxy)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1️⃣  PRIVACY — Server doesn't learn who you are
```
    └─ Without proxy: Server sees your real IP → tracks your location, browsing habits
    └─ With proxy: Server sees proxy IP → doesn't know it's YOU making the request
    └─ Example: Browsing amazon.com from your office. Company proxy hides it's the company network.

```

2️⃣  SECURITY — Prevent direct attacks on your device
```
    └─ Without proxy: Attacker knows your IP → can DDoS/hack YOUR device directly
    └─ With proxy: Attacker sees proxy IP → can't target your personal device
    └─ Example: Hacker finds a vulnerability, targets your IP instead of proxy (easier victim).

```

3️⃣  ACCESS CONTROL — Company enforces rules on employees
```
    └─ Without proxy: Employees access any website freely
    └─ With proxy: Company blocks sites (adult, gambling, social media)
    └─ Example: Bank employee tries to access Facebook → corporate proxy blocks it.

```

4️⃣  ANONYMITY — Browse without being tracked
```
    └─ Without proxy: Ad networks track your IP → serve targeted ads
    └─ With proxy: Ad networks see proxy IP → can't build profile on YOU
    └─ Example: ISP tracks your browsing → sells to advertisers. Proxy stops this.

```

5️⃣  COMPLIANCE — Meet legal/regulatory requirements
```
    └─ GDPR: Websites can't store real client IP (personal data)
    └─ Data residency: Company data must stay in country → use local proxy
    └─ Example: EU company behind proxy in EU region (can't be stored on US servers).

```

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Real-World Analogy:
Without Proxy: You write a letter with your home address → recipient knows where you live.
With Proxy: You send letter through a mail center (proxy) that only shows its address → 
            recipient can't know where you actually live.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Who Uses Forward Proxies:
```
├─ Employees (corporate VPN/proxy)
├─ ISP users (VPN services)
├─ Activists (circumvent censorship)
├─ Privacy-conscious users (avoid tracking)
└─ Companies (enforce policies + privacy)

```

🔙 REVERSE PROXY (Hides Server Identity):
Why Hide: Prevent attackers from discovering backend servers, prevent DDoS on specific servers, allow server swaps without client disruption, hide infrastructure details.
Benefits: Protects backend servers, load balances traffic, caches responses, routes intelligently.
Business: Netflix (hide server IPs, load balance), Facebook (hide backend farm), e-commerce 
          (handle spikes), API gateways (centralized security).

WHY HIDE SERVER IDENTITY (Reverse Proxy)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1️⃣  SECURITY — Prevent direct attacks on backend servers
```
    └─ Without proxy: Attacker knows your server IP → can exploit vulnerabilities directly
    └─ With proxy: Attacker sees proxy IP only → can't reach backend servers
    └─ Example: Hacker finds SQL injection bug. Without reverse proxy, hacks DB directly. 

```
               With proxy, attack hits proxy (hardened) instead of weak backend.

2️⃣  DDoS PROTECTION — Attackers can't flood specific servers
```
    └─ Without proxy: Attacker floods server IP with 1 million requests → server crashes
    └─ With proxy: Attacker floods proxy IP → proxy distributes to healthy backends
    └─ Example: Netflix gets DDoS attack. Proxy absorbs traffic, routes to working servers.

```
               Client never experiences outage.

3️⃣  HIDE INFRASTRUCTURE — Don't reveal backend architecture/topology
```
    └─ Without proxy: Attacker scans → finds you have 10 servers in California
    └─ With proxy: Attacker only sees 1 proxy → has no idea about backend setup
    └─ Example: Competitor can't copy your architecture. Security through obscurity.

```

4️⃣  LOAD BALANCING — Distribute traffic across servers transparently
```
    └─ Without proxy: Client requests go to static IP → single server gets overloaded
    └─ With proxy: Proxy routes to least-busy server → all servers equally loaded
    └─ Example: Instagram gets 1 million requests/second. Proxy spreads across 100 servers.

```
               Client thinks it's talking to 1 server, actually talking to 100.

5️⃣  SCALABILITY — Add/remove servers without client knowing
```
    └─ Without proxy: Need to update client code/DNS every time you add server
    └─ With proxy: Add server to backend pool → proxy automatically routes to it
    └─ Example: Amazon Black Friday traffic spike. Add 50 new servers. Clients see 0 change.

```
               Proxy handles routing, client IP stays same.

6️⃣  SERVICE ISOLATION — Multiple backends appear as single service
```
    └─ Without proxy: Service 1 on 10.0.0.1, Service 2 on 10.0.0.2 → confusing
    └─ With proxy: All services accessible via proxy.example.com → clean, unified interface
    └─ Example: Facebook.com routes to different services (photos, messages, ads).

```
               Client only sees facebook.com, not 50 different backend services.

7️⃣  MAINTENANCE — Take servers down without disrupting clients
```
    └─ Without proxy: Take server down → clients get errors
    └─ With proxy: Remove server from pool → proxy routes to others → zero downtime
    └─ Example: Need to update database server. Remove from proxy pool, update, add back.

```
               Users never see "service unavailable" error.

8️⃣  API GATEWAY — Centralized security, logging, rate limiting
```
    └─ Without proxy: Each backend implements security separately → inconsistent
    └─ With proxy: Proxy enforces security for ALL backends → single source of truth
    └─ Example: Rate limit 100 requests/minute. Proxy checks for all backends.

```
               Hacker can't bypass by hitting different backend directly.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Real-World Analogy:
Without Proxy: Restaurant has 10 kitchens on 10th, 11th, 12th floors. Customer sees each 
               kitchen address → can attack specific kitchen directly.
With Proxy: Customer only knows main entrance on ground floor (proxy). Inside, food gets 
            prepared in any of 10 kitchens. Customer has no idea where food comes from.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Who Benefits from Reverse Proxies:
```
├─ Netflix (hide 1000s of servers, load balance globally)
├─ Facebook (route to correct data center)
├─ E-commerce (handle Black Friday traffic spikes)
├─ Banks (security + DDoS protection)
├─ SaaS companies (multi-tenant routing)
└─ Any company needing 99.99% uptime

```

Memory Trick: 
  Forward = 👤 Protect CLIENT from server attacks & tracking
  Reverse = 🖥️ Protect SERVER from direct attacks & discovery

REVERSE PROXY, LOAD BALANCER, API GATEWAY — CRISP NOTES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

🎯 CORE CONCEPT:
Reverse Proxy = UMBRELLA (sits between client & backend)
Load Balancer, API Gateway, Cache, WAF = SPECIFIC ROLES of reverse proxy

Think: Reverse Proxy is "vehicle", Load Balancer is "ambulance" (type of vehicle)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

HIERARCHY:
REVERSE PROXY (parent)
```
├─ Load Balancer (distribute traffic across servers)
├─ API Gateway (auth, rate limiting, routing)
├─ Cache Proxy (cache responses)
├─ SSL/TLS Terminator (decrypt once)
└─ WAF (block malicious requests)

```

All handled by ONE software: nginx, HAProxy, AWS ELB, Cloudflare

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PHYSICAL vs LOGICAL:
LOGICAL = describes the role (load balancing, API gateway)
PHYSICAL = actual software implementation (nginx, AWS ELB)

Example: nginx (physical) can do all 5 roles above (logical)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TERMINOLOGY MAP:
Load Balancer    = Reverse Proxy distributing traffic
API Gateway      = Reverse Proxy + auth + rate limiting
Reverse Proxy    = Umbrella term for all
nginx/ELB        = Tools that implement reverse proxy
Cloudflare       = Reverse Proxy + CDN + Cache + WAF

All describe similar concept, different emphasis.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

IN INTERVIEWS:
Say: "Add reverse proxy (nginx/ELB) for:
```
      ├─ Load balancing
      ├─ Caching
      ├─ Rate limiting
      ├─ SSL termination"

```

Don't worry about exact terminology. Focus on what it does.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

KEY INSIGHT:
Reverse Proxy = WHAT (concept)
nginx/AWS ELB = HOW (tool)

One tool, many roles. Don't overthink names.

## HOW WE ARRIVE AT 60% UTILIZATION

STEP 1: CALCULATE TRAFFIC

Given:
```
├─ 1 million DAU
├─ Each loads feed 5 times/day
└─ = 5 million requests/day

```

Convert to requests per second:
```
├─ 5 million requests / 86,400 seconds (per day)
├─ = 57.87 req/sec average
└─ ≈ 58 req/sec (baseline/average traffic)

```

STEP 2: ESTIMATE PEAK TRAFFIC

Assume peak is 3x average:
```
├─ Peak traffic = 58 × 3
├─ = 174 req/sec at peak
└─ (This is when most users are active - morning/evening)

```

STEP 3: DEFINE TARGET UTILIZATION

Here's the key question:
"At peak traffic, what % of my server capacity should I use?"

Options:
```
├─ 90% utilization: Cheap but risky (no headroom)
├─ 70% utilization: Medium (some headroom)
├─ 60% utilization: Industry standard (good balance)
├─ 40% utilization: Conservative (expensive but safe)
└─ 20% utilization: Wasteful (too much idle capacity)

```

Industry standard = 60% utilization at peak

Why 60%?
```
├─ Leaves 40% headroom for unexpected spikes
├─ Handles failovers (if 1 server fails, others absorb load)
├─ Allows for graceful degradation
├─ Provides buffer for garbage collection, context switching
├─ Room for hotspots and uneven distribution
└─ Not too wasteful, not too risky

```

STEP 4: CALCULATE REQUIRED CAPACITY

Formula:
```
├─ Required Capacity = Peak Traffic / Target Utilization %
├─ Required Capacity = 174 req/sec / 0.60
├─ = 290 req/sec capacity needed

```

Meaning:
```
├─ Peak traffic = 174 req/sec
├─ Running at 60% of your capacity
├─ Total capacity = 290 req/sec
└─ Headroom = 290 - 174 = 116 req/sec (unused)

```

STEP 5: SIZE YOUR FLEET

If each server can handle 10 req/sec:
```
├─ Servers needed = 290 / 10
├─ = 29 servers
└─ At peak: 174/290 = 60% utilized ✓

```

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

VISUALIZATION: WHY 60% NOT 100%

100% Utilization (BAD):
```
├─ Average traffic: 58 req/sec
├─ Peak traffic: 174 req/sec
├─ Capacity: 174 req/sec (just enough for peak)
├─ If traffic spikes beyond peak → OVERLOAD ❌
├─ If 1 server fails → Can't absorb ❌
├─ If garbage collection pause → Queue builds up ❌
└─ One small unexpected event = disaster!

```

60% Utilization (GOOD):
```
├─ Average traffic: 58 req/sec
├─ Peak traffic: 174 req/sec
├─ Capacity: 290 req/sec (extra headroom)
├─ If traffic spikes beyond peak → Still OK ✓
├─ If 1 server fails → Others can absorb ✓
├─ Garbage collection pause → Just dips to 70% ✓
└─ Built-in safety buffer!

```

Visual:
```
┌────────────────────────────────────────────────────┐
│ 100% Utilization Approach (Risky)                  │
├────────────────────────────────────────────────────┤
│ Capacity:  [================================================]
│ Average:   [======================================]
│ Peak:      [================================================]
│ Problem:   No headroom! Any spike = failure! ❌   │
└────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────┐
│ 60% Utilization Approach (Safe)                    │
├────────────────────────────────────────────────────┤
│ Capacity:  [================================================]
│ Average:   [======================]
│ Peak:      [==========================]  ← 60% full
│ Headroom:  [========================]  ← 40% buffer ✓
│ Benefit:   Room for spikes, failovers, GC! ✓      │
└────────────────────────────────────────────────────┘

```

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY NOT DIFFERENT PERCENTAGES?

80% Utilization:
```
├─ Pro: Saves money (fewer servers)
├─ Con: Only 20% headroom (risky)
├─ Use: Non-critical systems

```

60% Utilization:
```
├─ Pro: Good balance (40% headroom)
├─ Con: Costs more than 80%
├─ Use: Standard production systems (INDUSTRY STANDARD)

```

40% Utilization:
```
├─ Pro: Very safe (60% headroom)
├─ Con: Expensive (many idle servers)
├─ Use: Critical systems (banking, healthcare)

```

The 60% "magic number" is:
```
├─ High enough to be cost-effective
├─ Low enough to be safe
├─ Proven by industry experience
└─ Not arbitrary - it's a learned optimum

```

COMPLETE CALCULATION EXAMPLE

Given: 1M DAU, 5 loads/day, each request takes 100ms

Step 1: Average traffic
```
├─ 5M requests/day
├─ = 58 req/sec average

```

Step 2: Peak traffic (assume 3x)
```
├─ Peak = 174 req/sec

```

Step 3: Latency target
```
├─ p99 < 300ms
├─ Each request takes ~100ms
├─ Queue time budget: 300ms - 100ms = 200ms

```

Step 4: Little's Law to estimate queue length
```
├─ L = λ × W
├─ L = 174 × 0.2 = 34.8 requests in queue at peak
└─ Reasonable (not too high)

```

Step 5: Target utilization
```
├─ Set to 60% (industry standard)

```

Step 6: Required capacity
```
├─ Capacity = 174 / 0.60 = 290 req/sec

```

Step 7: Server sizing (assume 10 req/sec per server)
```
├─ Servers = 290 / 10 = 29 servers
├─ At average: 58/290 = 20% utilized (good headroom)
├─ At peak: 174/290 = 60% utilized (target hit!)
└─ Headroom: 116 req/sec for spikes

```

Interview statement:
"I'm sizing for 3x average traffic (174 req/sec peak) and running at 60%
utilization at peak, which gives me 29 servers with room for failover and
unexpected spikes. P99 latency should stay under 300ms."

KEY INSIGHT

60% utilization is not:
```
├─ A formula
├─ A law of physics
├─ Something from a textbook
└─ Random

```

60% utilization IS:
```
├─ Industry best practice (proven in production)
├─ A balance point (cost vs safety)
├─ A communication shorthand
├─ A way to show you understand trade-offs

```

When interviewer hears "60% utilization at peak":
✓ "This person understands capacity planning"
✓ "They know the cost/safety trade-off"
✓ "They're being practical (not 100%, not 20%)"
✓ "They can defend their sizing decisions"

